# AWS 에이전트 샌드박스 실측 비교

[English](README.md)

같은 Claude Agent SDK 앱을 AWS의 샌드박스 다섯 가지에 올리고, 같은 리전에 둔 측정기에서 측정했습니다. 2026-11-03~05에 `us-east-1`에서 여러 라운드와 후속 실험을 진행했고, 일부는 `ap-northeast-1`에서 다시 측정했습니다. 2026-11-10에는 EKS Fargate와 Nitro Sandboxes를 같은 실험으로 추가 측정했습니다. 모든 수치는 `results/raw/`의 원시 데이터에서 생성합니다. 별도 표시가 없으면 측정값입니다. 문서에서 가져온 값에는 (문서), 실험하지 않은 항목에는 n/t를 붙였습니다.

## 결과는 달라질 수 있습니다

이 결과는 대부분 한 리전(us-east-1)에서 나왔고, 일부만 도쿄(ap-northeast-1)에서 다시 측정했습니다. 사흘 동안(Fargate와 Nitro는 하루 더) 한 계정에서 앱 하나로 측정한 결과입니다. 리전, 쿼터, 계정 한도, 가용 용량, 인스턴스 종류, 이미지, 애플리케이션, 시간대에 따라 결과가 달라질 수 있습니다. 출발점으로 참고하시고, 결정하기 전에 실제로 운영할 에이전트로 다시 측정해 보시기 바랍니다.

## 상세 결과

별도 표시가 없으면 p50입니다. 신뢰 구간이 겹치면 차이가 있다고 보지 않습니다. 첫 메시지는 SDK를 import한 뒤 `query()`를 호출한 시점부터 SDK가 첫 객체를 돌려줄 때까지의 시간으로, 첫 모델 스트림 이벤트보다 앞섭니다. 샌드박스 시작과 SDK import 시간은 들어 있지 않습니다. 전체 시간은 샌드박스 시작 시간과 에이전트 호출 시간을 더한 값으로, SDK import, 태스크, 하네스의 pytest, 네트워크 시간이 모두 들어 있습니다.

### EKS Fargate와 Nitro Sandboxes (2026-11-10 추가)

다른 구성을 측정하고 닷새 뒤에 같은 앱과 같은 실험으로 두 가지를 더 측정했습니다. **EKS Fargate**는 기존 클러스터에 Fargate 프로필을 추가해 샌드박스 Pod마다 Fargate microVM을 따로 띄웁니다. **Nitro Sandboxes**(2026-11-09 발표)는 `runtimeClassName: isolated-sandbox`를 지정하면 Pod마다 Nitro 하이퍼바이저 위에 VM을 따로 띄웁니다. Auto Mode에 런타임이 들어 있고 기존 클러스터에는 이미 Karpenter가 있어서, 같은 VPC와 서브넷에 EKS Auto Mode 클러스터를 따로 만들고 x86 노드 그룹과 같은 m8i.2xlarge, 같은 가용 영역에서 측정했습니다. 두 구성 모두 Pod의 limits가 아니라 requests로 VM 크기를 정합니다. 그래서 작은 크기(0.25 vCPU, 512 MiB)로 echo, 버스트, 유입을 측정하고, 다른 샌드박스의 한도와 같은 2 vCPU, 8 GB 크기로 에이전트, 빌드, 워크로드를 측정했습니다. 기준선으로 Fargate는 gVisor, V1과, Nitro는 gVisor, Kata와 같은 시간대에 함께 측정했습니다.

Fargate는 이전 세대 CPU(Xeon Platinum 8259CL)에서 실행돼 순수 Python이 약 두 배 오래 걸렸고, 시스템 콜과 파일 작업도 더 느렸습니다. 두 구성 모두 게스트 커널이 따로 있습니다. Nitro는 호스트 6.18.56 위에서 게스트 6.18.54, Fargate는 6.1.189입니다.

Nitro에서 EBS 볼륨을 붙인 채 agent-sandbox의 `operatingMode`를 `Suspended`로 바꿨다가 다시 `Running`으로 돌렸습니다. 매 사이클마다 새 10 GiB gp3 볼륨을 붙인 샌드박스를 만들고, 볼륨의 파일과 프로세스 메모리에 값을 쓴 뒤 중지, 재개하고 두 값을 다시 읽었습니다.

에이전트 동시 실행(전체 시간, 4배치): Nitro는 동시 5개 15.1초, 20개 16.3초, Fargate는 65.8초, 67.2초였고 실패는 0회입니다. 2 vCPU, 8 GB Nitro 샌드박스는 메모리를 모두 예약하므로 m8i.2xlarge 한 대에 3개만 들어가고, 동시 20개에는 노드가 최소 7대 필요합니다. 새 샌드박스에서 331 MB CLI 첫 읽기는 Fargate 0.05초, Nitro 0.51초로, V2와 MicroVM의 첫 읽기 지연이 없습니다.

보안 기본값은 아래 표와 같은 방식으로 점검했고 강화 설정은 하지 않았습니다. 두 구성 모두 SA 토큰이 마운트되고, Kubernetes API, 다른 샌드박스, 인터넷에 연결할 수 있으며, CAP_SYS_ADMIN과 /dev/kvm은 없습니다. Nitro는 IMDS에 응답하지만 허용된 경로만 열려 있어 역할이 보이지 않고, 자격 증명은 Pod Identity로 받습니다. Fargate는 IMDS가 없습니다. Fargate에서는 Pod Identity가 동작하지 않아 IRSA를 썼고, DaemonSet도 실행되지 않습니다.

EKS는 실험한 그대로이며 강화 설정을 적용하지 않았습니다. AWS 블로그 시리즈는 Pod Security restricted, non-root 실행, capability 제거, SA 토큰 끄기를 권장하지만 이 표에는 적용하지 않았습니다. Warm Pool 템플릿은 토큰을 마운트하지 않았습니다. Pod Identity 접근 여부는 네트워크 정책을 켠 상태(시간 초과)만 기록했고 기본 상태는 기록하지 않았습니다. MicroVM의 인터넷 외부 통신은 커넥터로 명시적으로 열었습니다.

## 측정 방법

- **같은 앱.** `app/`는 Claude Agent SDK를 담은 이미지 하나입니다. MicroVM은 이 이미지를 `FROM`으로 빌드하고, EKS와 AgentCore는 이 이미지를 그대로 씁니다. 샌드박스 한도는 2 vCPU, 8 GiB입니다. MicroVM만 과금 기준이 4 GB, 2 vCPU이고 8 vCPU가 보입니다.
- **같은 리전.** 측정기를 포함해 모두 `us-east-1`에서 실행했습니다. 도쿄 재측정은 측정기도 `ap-northeast-1`에 두었습니다. 다만 호출 경로는 다릅니다. EKS는 Pod IP로, 관리형은 공용 엔드포인트로 호출합니다.
- **같은 정의.** 샌드박스를 요청하는 첫 호출 직전부터 앱이 응답할 때까지를 측정합니다. 에이전트 준비 시간은 따로 측정합니다.
- **대조군.** 같은 노드의 runc, 관리형과 CPU를 맞춘 Graviton3의 gVisor와 runc, 중첩 가상화의 영향을 분리하기 위한 `m8i.metal-48xl`의 Kata를 두었습니다.
- **용량과 쿼터로 인한 불이익 배제.** 쿼터나 노드 부족이 결과를 정한 경우는 제외하거나 다시 측정했습니다.
- **순서와 실패.** 대표 에이전트 표와 콜드 스타트 표는 사이클마다 백엔드 순서를 섞어, 특정 구성이 특정 시간대에 몰리지 않게 했습니다. 후속 비교(완화책, SDK, 네트워크 모드, 빌드, 동시 실행)도 각각 같은 시간대에 조건 순서를 섞었습니다. 메탈은 따로 실행했습니다. 실패도 모두 기록하고 집계하며, 시간 집계에서는 실패만 빼고 느린 실행은 그대로 둡니다.
- **주장 검증.** 문서의 주장이 데이터와 맞지 않으면 `analysis/verify_claims.py`가 실패합니다.

## 이 실험의 한계

- 대부분 한 리전에서 측정했고 도쿄에서는 일부만 다시 측정했습니다. 사흘 동안 한 계정에서 앱 하나로 측정했으므로, 리전, 쿼터, 용량, 시간에 따라 결과가 달라질 수 있습니다. 첫 읽기 결과는 에이전트가 처음 읽는 파일의 크기에 따라 달라집니다.
- 플랫폼마다 네트워크 경로가 달라서 왕복 시간은 런타임만 비교한 값이 아닙니다.
- 이 실험은 첫 읽기가 언제 느리고 무엇으로 해결되는지를 보여 줄 뿐, 플랫폼 내부에서 왜 느린지는 다루지 않습니다.
- Kata는 기본 virtio-fs로 실행했습니다. 블록 디바이스 rootfs와 메모리 기반 작업 디렉터리는 실험하지 않았습니다.
- 실험하지 않은 항목: 8시간과 14일 세션, Spot, KVM 플랫폼의 gVisor, 쿼터를 올린 MicroVM, EKS 강화 옵션, X-Ray 트레이스, 서울 리전, 도쿄의 MicroVM과 Warm Pool, V1과 MicroVM의 세션 스토리지.
- 일부 후속 실험은 표본이 적습니다(8~16회). 신뢰 구간을 함께 보세요. Strands 앱은 도구 3개로 직접 만든 앱입니다.
- Fargate와 Nitro는 다른 구성보다 닷새 늦게 하루 동안 측정했고, 같은 시간대의 기준선과 비교했습니다. Nitro는 같은 VPC와 가용 영역에 둔 별도 Auto Mode 클러스터에서 별도 측정기로 측정했습니다. Nitro는 isolated 모드만 실험했고, 네트워크와 DNS 한도는 기본값을 썼습니다.
- 보안 결과는 기본값을 설명할 뿐 탈출 내성을 평가한 것이 아닙니다.
- 비용 시나리오의 트래픽은 가정입니다. AgentCore 약정 가격은 제공 여부를 확인하지 못해 쓰지 않았습니다.
- `results/raw/`에는 표에서 뺀 실행도 남아 있습니다. `cold_uncached.jsonl`은 무효 실험입니다.

## 구성과 재현

```
app/        에이전트 이미지, 워크로드, 프로브
bench/      측정기: 백엔드, 실험, 배포. 후속 실험은 bench/followup/
infra/      Terraform과 Kubernetes 매니페스트
scripts/    라운드 실행 체인, 결과 동기화
analysis/   요약, 사실 추출, 비용 모델, 주장 검증, README 생성
results/    원시 JSONL과 생성된 요약(계정 ID 제거)
```

```bash
cd infra/terraform && terraform init && terraform apply
# infra/k8s/*.yaml의 ACCOUNT_ID를 바꾸고, Dockerfile*로 이미지를 빌드하고, agent-sandbox와 kata-deploy를 설치

# bench/와 scripts/를 드라이버 Pod에 복사한 뒤:
python deploy.py --which all
sh /work/scripts/chain_r1.sh
sh /work/scripts/chain_same.sh
scripts/pull_results.sh
python3 analysis/analyze.py && python3 analysis/cost_model.py && python3 analysis/followup.py && python3 analysis/facts.py
python3 analysis/verify_claims.py && python3 analysis/make_readme.py
```

**이 환경은 실험용으로 쓰고 버리는 구성이며 참조 아키텍처가 아닙니다.** 드라이버에 cluster-admin 권한이 있고, 노드에서 특권 도우미가 실행되며, 앱 엔드포인트는 VPC 안에서 인증 없이 열려 있고, IAM 권한도 넓으며, EKS API 엔드포인트가 공개되어 있습니다. `infra/terraform/iam.tf`의 주석을 참고하세요. 실험이 끝나면 삭제하세요.
