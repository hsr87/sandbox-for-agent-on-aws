# AWS 에이전트 샌드박스 실측 비교

[English](README.md)

같은 Claude Agent SDK 앱을 AWS의 샌드박스 다섯 가지에 올리고, 같은 리전의 측정기에서 쟀습니다. `us-east-1`에서 2026-11-03~04에 여러 라운드와 후속 시험을 돌렸습니다. 측정 숫자는 `results/raw/`에서 생성합니다. 표시가 없으면 측정값이고, 문서에서 가져온 값은 (문서), 시험하지 않은 항목은 n/t로 표시합니다.

## 결과는 달라질 수 있습니다

이 결과는 한 리전(us-east-1), 이틀, 한 계정, 앱 하나에서 나왔습니다. 리전, 쿼터, 계정 한도, 가용 용량, 인스턴스 종류, 이미지, 애플리케이션, 시간대에 따라 달라질 수 있습니다. 출발점으로 삼고, 결정 전에 자사 에이전트로 다시 측정해 보시기 바랍니다.

## 결과

표시가 없으면 p50입니다. 신뢰 구간이 겹치면 차이로 보지 않습니다. 첫 메시지는 SDK import 뒤 `query()`를 호출한 때부터 SDK가 첫 객체를 줄 때까지로, 첫 모델 스트림 이벤트보다 앞선 시점입니다. 샌드박스 시작과 SDK import는 빠집니다. 요청 전체는 샌드박스 시작과 에이전트 호출을 더한 값으로, SDK import, 태스크, 하네스의 pytest, 네트워크가 들어 있습니다.

VPC CNI NetworkPolicy를 켜자 Warm Pool 샌드박스에서: 다른 샌드박스 timeout, Kubernetes API timeout, 인터넷 open, Pod Identity 엔드포인트 TimeoutError. Agent Sandbox가 만든 정책은 169.254.0.0/16을 제외하므로, gVisor와 Kata 모두 AWS 자격 증명 조회가 CredentialRetrievalError로 실패했습니다. Pod Identity 엔드포인트에 예외를 넣거나 자격 증명을 다른 방식으로 주입해야 합니다. SandboxTemplate 없이 직접 만든 Sandbox는 정책이 없어 그대로 열려 있었습니다.

샌드박스 안에서 기본값을 확인한 무해한 점검이며 침투 시험이 아닙니다. 탈출 내성에 대해서는 아무것도 말하지 않습니다. 메타데이터로 보이는 역할은 그 세션의 실행 역할입니다. 관리형 세션은 같은 링크 로컬 주소를 쓰므로 세션 간 시험으로는 격리를 판정할 수 없었고, 격리를 주장하지 않습니다.

EKS는 시험한 그대로이며 강화하지 않았습니다. AWS 블로그 시리즈는 Pod Security restricted, non-root, capability 제거, SA 토큰 끄기를 권장하며, 이 표에는 적용하지 않았습니다. Warm Pool 템플릿은 토큰을 마운트하지 않았습니다. Pod Identity 도달 여부는 네트워크 정책을 켠 상태(시간 초과)만 기록했고, 기본 상태는 기록하지 않았습니다. MicroVM의 인터넷 외부 통신은 커넥터로 명시적으로 요청했습니다.

| 플랫폼 지표 | 이번 구성에는 없음. Container Insights 같은 EKS 애드온은 설치, 평가하지 않음 | Invocations, Sessions, Latency, Throttles, OverheadLatency, vCPU, memory | 계정 CloudWatch 전체 조회에서 서비스 지표 없음(로그 수신 지표만) |

| 컨트롤 플레인 로그 | 5종 모두 기본 꺼짐 | CloudTrail (doc) | CloudTrail (doc) |

### 밀도와 실행 환경

유휴 샌드박스당 호스트 메모리: runc 32 MB, gVisor 58 MB, Kata 375 MB. Kata의 RuntimeClass는 Pod당 CPU 250m를 더하므로, 요청 250m 기준 노드당 수용량이 절반 정도로 줄어듭니다.

## 방법

- **같은 앱.** `app/`는 Claude Agent SDK가 든 이미지 하나입니다. MicroVM은 이 이미지를 `FROM`으로 빌드하고, EKS와 AgentCore는 그대로 가져옵니다. 샌드박스 한도는 2 vCPU, 8 GiB이며 MicroVM만 과금 기준 4 GB, 2 vCPU에 8 vCPU가 보입니다.
- **같은 리전.** 측정기까지 모두 `us-east-1`입니다. 경로 차이는 남습니다. EKS는 Pod IP로, 관리형은 공용 엔드포인트로 호출합니다.
- **같은 정의.** 샌드박스를 요청하는 첫 호출 직전부터 앱이 답할 때까지 잽니다. 에이전트 준비 시간은 따로 잽니다.
- **대조군.** 같은 노드의 runc, 관리형과 같은 CPU의 Graviton3 위 gVisor와 runc, 중첩 가상화를 분리하기 위한 `m8i.metal-48xl` 위 Kata.
- **용량과 쿼터의 불이익 없음.** 쿼터나 노드 부족이 정한 결과는 빼거나 재측정했습니다.
- **순서와 실패.** 대표 에이전트와 콜드 스타트 표는 사이클마다 백엔드 순서를 섞었습니다. 빌드, 완화책, 메탈은 각자의 시기에 돌렸습니다. 실패도 기록하고 집계하며, 시간 집계에서는 실패만 뺍니다. 느린 실행은 그대로 둡니다.
- **주장.** `analysis/verify_claims.py`는 주장이 깨지면 실패합니다.

## 이 실험의 한계

- 한 리전, 이틀, 한 계정, 앱 하나입니다. 결과는 리전, 쿼터, 용량, 시간에 따라 달라질 수 있습니다. 첫 읽기 결과는 이 SDK의 큰 CLI 바이너리에 좌우됩니다.
- 플랫폼마다 네트워크 경로가 달라 왕복은 런타임만의 비교가 아닙니다.
- 느린 첫 읽기의 원인은 저희 해석이며 AWS의 설명이 아닙니다.
- Kata는 기본 virtio-fs로 돌렸습니다. 블록 디바이스 rootfs와 메모리 기반 작업 디렉터리는 시험하지 않았습니다.
- 시험하지 않은 것: 8시간과 14일 세션, Karpenter, Spot, KVM 플랫폼의 gVisor, MicroVM 쿼터 증설 후, EKS 강화 옵션, 세션 스토리지, X-Ray 트레이스, 서울과 다른 리전.
- 일부 후속 시험은 표본이 적습니다(8~12회). 신뢰 구간을 함께 보세요.
- 보안 결과는 기본값 설명이며 탈출 내성에 대한 진술이 아닙니다.
- 비용 시나리오의 트래픽은 가정입니다. AgentCore 약정 가격은 상태를 확인하지 못해 쓰지 않았습니다.
- `results/raw/`에는 표에서 뺀 실행도 남아 있습니다. `cold_uncached.jsonl`은 무효 실험입니다.
